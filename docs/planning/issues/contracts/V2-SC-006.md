# V2-SC-006 — Implement Deterministic Claim Registry and Creation Flow

## Overview

Implement canonical claim creation, collision-resistant identifiers, bounty intake, parameter binding, and the initial VerificationOpen state.

## Problem Context

V2 requires claims to originate through user-signed on-chain transactions. Existing backend-owned creation paths and legacy identifiers cannot remain authoritative.

This issue belongs to **V2-EPIC-SC-001 — Canonical Contract Topology and Deployment**. Existing repository issues are historical only; their titles, labels, closure state, or partial implementations do not satisfy this issue.

## Technical Scope

- Derive claim IDs from chain ID, registry address, submitter, consumed submitter nonce, and metadata digest.
- Validate supported asset, bounty range, metadata/evidence digest formats, and active configuration version.
- Transfer the exact supported bounty amount using safe token semantics and record custody reference.
- Store the minimal canonical claim record and emit ClaimCreated with the fields required for replay.

The contributor must begin by auditing current files that overlap this scope. Reusable logic may be retained only when it conforms to the governing V2 interfaces, events, authority boundaries, and tests. The pull request must identify reused, replaced, and deprecated paths.

## Security and Integrity Requirements

- Use reentrancy protection and checks-effects-interactions.
- Reject zero digests, duplicate identifiers, non-standard unsupported assets, and zero recipients.
- Ensure nonce consumption and bounty transfer are atomic.
- Preserve blockchain authority and every applicable protocol invariant.
- Do not add secrets, production credentials, dummy production addresses, backend settlement authority, or Stellar/Freighter runtime dependencies.

## Required Tests

- Happy-path creation with multiple users and nonces.
- Collision, replay, unsupported asset, insufficient allowance, and transfer-failure tests.
- Fuzz tests for metadata digests, nonce ranges, and bounty bounds.
- Run the repository’s complete required Hardhat and Foundry suites and report unrelated pre-existing failures separately.
- Add regression coverage for every defect or unsafe legacy behavior removed by this work.

## Acceptance Criteria

- [ ] Every accepted claim has one deterministic ID and one locked bounty.
- [ ] No claim record exists after a failed transfer.
- [ ] The claim references an immutable parameter version.
- [ ] ClaimCreated can reconstruct the initial record.
- [ ] All new and existing relevant tests pass on the final commit.
- [ ] Static analysis and formatting introduce no new unresolved finding.
- [ ] Documentation and generated artifacts affected by the change are current.
- [ ] The pull request maps evidence to every acceptance criterion.
