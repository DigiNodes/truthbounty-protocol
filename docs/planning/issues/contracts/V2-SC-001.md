# V2-SC-001 — Define Canonical V2 Contract Interfaces

## Overview

Create the authoritative Solidity interfaces for every V2 module and define which calls are state-changing, read-only, governance-only, or internal coordination.

## Problem Context

Existing contracts expose overlapping and incompatible entry points, which lets deployment, indexer, and frontend work target different protocol shapes. The modular V2 suite needs one reviewed interface surface before implementation modules evolve further.

This issue belongs to **V2-EPIC-SC-001 — Canonical Contract Topology and Deployment**. Existing repository issues are historical only; their titles, labels, closure state, or partial implementations do not satisfy this issue.

## Technical Scope

- Add interfaces for configuration, module registry, claims, evidence, stake custody, verification, aggregation, settlement, disputes, rewards, slashing, treasury, reputation roots, governance hooks, and emergency controls.
- Use explicit NatSpec for caller permissions, state effects, return values, emitted events, and revert conditions.
- Separate external user actions from module-to-module hooks and expose interface IDs where ERC-165 adds value.
- Add an interface ownership table in contract-specific documentation and map every method to Protocol V2 Specification sections.

The contributor must begin by auditing current files that overlap this scope. Reusable logic may be retained only when it conforms to the governing V2 interfaces, events, authority boundaries, and tests. The pull request must identify reused, replaced, and deprecated paths.

## Security and Integrity Requirements

- Do not introduce privileged settlement or treasury shortcuts.
- Avoid interfaces that require unbounded arrays or push-based batch payouts.
- Document trust boundaries for every cross-module call and reject zero-address dependencies.
- Preserve blockchain authority and every applicable protocol invariant.
- Do not add secrets, production credentials, dummy production addresses, backend settlement authority, or Stellar/Freighter runtime dependencies.

## Required Tests

- Compile-time interface conformance fixtures for representative modules.
- Selector-collision and ERC-165 support tests where applicable.
- Negative tests showing deprecated legacy methods are absent from canonical interfaces.
- Run the repository’s complete required Hardhat and Foundry suites and report unrelated pre-existing failures separately.
- Add regression coverage for every defect or unsafe legacy behavior removed by this work.

## Acceptance Criteria

- [ ] All canonical module responsibilities have a named interface.
- [ ] No interface grants the API, treasury, or guardian authority to decide claim outcomes.
- [ ] NatSpec and ownership mapping pass review.
- [ ] Hardhat and Foundry compilation succeeds without new warnings.
- [ ] All new and existing relevant tests pass on the final commit.
- [ ] Static analysis and formatting introduce no new unresolved finding.
- [ ] Documentation and generated artifacts affected by the change are current.
- [ ] The pull request maps evidence to every acceptance criterion.

## Deliverables

- Production-quality Solidity, interfaces, libraries, deployment code, or test code required by the scope.
- Unit and higher-level tests described above.
- NatSpec and contract-specific technical documentation.
- A pull-request summary covering architecture, security analysis, gas or storage impact, migration implications, and residual risks.
- Evidence of commands run and their results.

## Dependencies

- No V2 contract issue dependency. The merged V2 specification, engineering blueprint, ADR-0001, and Wave operations policy are governing prerequisites.

This issue must not be assigned while any required dependency is unresolved or incompatible with the reviewed interface version.

## Non-Goals

- Implementing full module storage or business logic.
- Maintaining ABI compatibility with deprecated V1 authority paths.
- Creating, modifying, reopening, or relabelling historical GitHub issues.
- Applying the external `Stellar Wave` label.
