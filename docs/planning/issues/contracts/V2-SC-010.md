# V2-SC-010 — Implement Verification Submission Registry

## Overview

Implement first-round verification submission and canonical position storage.

## Problem Context

V2 needs immutable, stake-backed verification positions. Existing vote paths may accept duplicates, changeable positions, or records without enforceable stake.

This issue belongs to **V2-EPIC-SC-001 — Canonical Contract Topology and Deployment**. Existing repository issues are historical only; their titles, labels, closure state, or partial implementations do not satisfy this issue.

## Technical Scope

- Accept True or False only while the claim is VerificationOpen.
- Lock stake atomically through StakeVault and bind the lock to claim and round.
- Reject a second verification from the same address in the same round.
- Freeze submitted position, principal, submission time, and effective-weight input reference.
- Emit VerificationSubmitted and StakeLocked consistently.

The contributor must begin by auditing current files that overlap this scope. Reusable logic may be retained only when it conforms to the governing V2 interfaces, events, authority boundaries, and tests. The pull request must identify reused, replaced, and deprecated paths.

## Security and Integrity Requirements

- No verification record may exist without a successful stake lock.
- Prevent position changes, withdrawals, and replay.
- Use bounded enumeration or paginated getters to avoid settlement denial of service.
- Preserve blockchain authority and every applicable protocol invariant.
- Do not add secrets, production credentials, dummy production addresses, backend settlement authority, or Stellar/Freighter runtime dependencies.

## Required Tests

- Successful submissions across multiple claims and assets.
- Duplicate, invalid position, late, paused, insufficient allowance, and transfer-failure tests.
- Atomicity test proving failed locks create no vote.
- Fuzz tests for stake bounds.
- Run the repository’s complete required Hardhat and Foundry suites and report unrelated pre-existing failures separately.
- Add regression coverage for every defect or unsafe legacy behavior removed by this work.

## Acceptance Criteria

- [ ] One address has at most one position per round.
- [ ] Stored principal matches the vault lock.
- [ ] All rejection paths use precise errors.
- [ ] Events contain enough data for indexer projection.
- [ ] All new and existing relevant tests pass on the final commit.
